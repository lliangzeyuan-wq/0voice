
# 一句话结论

看着效果一样（都是echo回包），但**设计思想完全不一样**：

- 老版本：`recv_cb` 里面直接调用 `send()` → **同步发送**，收完立刻尝试发
- 新版本：`recv_cb` 只把收到的数据放进缓冲区，然后注册 `EPOLLOUT`；等到epoll检测到socket可写时，才调用`send_cb`发送 → **异步写（事件驱动发送）**

> 只有在**网络很好、发送缓冲区永远有空**的时候，两者表现一模一样；一旦网络拥塞、对端接收慢，差距立刻显现。

## 1. 直接在recv_cb里面send（同步发送）有什么问题

```
//旧写法，收到直接send
int recv_cb(int fd)
{
    recv(...)
    send(fd, buffer, idx, 0); // 收完马上调用send
}
```

send函数行为：

1. 如果内核发送缓冲区**有足够空间**：数据拷贝进内核缓冲区，send立刻返回，很快。
2. 如果内核发送缓冲区**满了**：
    - 当前socket是**阻塞fd**：`send()`直接阻塞！整个epoll主线程卡住，**所有其他连接全部停止响应，服务卡死**。
    - 如果改成非阻塞fd：`send()`返回-1，errno=EAGAIN，**剩下的数据发不出去，丢包**。

👉 这就是核心痛点：**不能保证send一定能一次性把数据全部发出去**。

## 2. 分离成 recv_cb + send_cb（EPOLLOUT事件驱动）的好处

```
recv_cb：接收数据，放到用户层buffer，注册EPOLLOUT事件
send_cb：epoll触发EPOLLOUT时，才去发送buffer里缓存的数据
```

### 好处1：解决发送缓冲区满的场景，支持**分片发送**   ==（我现在的代码还没有实现）==

当发送缓冲区满：

1. `send()` 只发出去一部分数据，返回值 < 待发送长度
2. 我们更新用户缓冲区，保留剩下还没发完的数据
3. **不修改epoll事件，继续监听EPOLLOUT**
4. 等内核发送缓冲区腾出空间，epoll自动触发EPOLLOUT，再次进入send_cb继续发剩下的内容
    
    > 数据存在应用层buffer里，不会丢。
    

> 这种机制叫**应用层发送缓冲区**，是Reactor模型标准写法，用来处理TCP的**部分写(partial write)**。

### 好处2：解耦「读事件」和「写事件」逻辑

- recv_cb 只管**收数据、组装报文**，不用关心能不能发出去
- send_cb 只管**往外发缓存好的数据**，不用关心数据哪来的 两个回调各司其职。后续扩展很方便：
- 比如：收到数据之后**不马上回复**，做计算/数据库查询，做完再往buffer塞数据，注册EPOLLOUT发送
- 比如：多客户端之间转发消息，A客户端收到的数据，放到B客户端的发送buffer，注册B的EPOLLOUT发送
！
> 如果是recv里面直接send，这种延迟回复、消息转发场景根本做不了。

### 好处3：不会阻塞epoll主线程

只要socket设置为非阻塞：send不会阻塞，无论缓冲区是否满，函数立刻返回，epoll事件循环持续跑，其他连接不受影响。

## 3. 为什么你现在测试感觉效果完全一样？

因为你的测试环境是本机： 客户端和服务器都在同一台机器，内核TCP发送缓冲区很大，**每次调用send的时候缓冲区一定有空位**，send一次就全部发完，不会出现partial write。 所以两种写法表现完全相同。

> 一旦放到真实网络：跨机器、弱网、客户端接收慢，`recv_cb`内直接send的写法就会出现阻塞或者丢包；而事件驱动EPOLLOUT写法依然稳定。

## 4. 看你截图里代码还存在一个小缺陷

```
int send_cb(int fd)
{
    char * buffer = connlist[fd].buffer;
    int idx = connlist[fd].idx;
    int count = send(fd , buffer , idx , 0);
    //event
    struct epoll_event ev;
    ev.events = EPOLLIN; //LT水平触发
    ev.data.fd = fd;
    epoll_ctl(epfd, EPOLL_CTL_MOD, fd, &ev);
    return count;
}
```

这里：

1. 没有判断send返回值，**没有处理只发送一部分的场景**
2. 没有更新`connlist[fd].idx`，没有移动buffer剩余数据
3. 不管send发没发完，直接切回EPOLLIN 如果send只发出去一部分，剩下数据就留在buffer里丢失了。

### send_cb 标准正确逻辑伪代码

```
int send_cb(int fd)
{
    buffer = connlist[fd].buffer;
    idx = connlist[fd].idx;
    count = send(fd, buffer, idx, 0);
    if(count <=0) {
        //出错，关闭连接
        return -1;
    }
    // 更新还剩多少数据没发
    connlist[fd].idx -= count;
    // 把未发送的数据前移到buffer头部
    memmove(buffer, buffer + count, connlist[fd].idx);

    if(connlist[fd].idx == 0)
    {
        // ✅全部发完，切回监听读事件，等待客户端下一条消息
        ev.events = EPOLLIN;
        epoll_ctl(MOD, &ev);
    } else {
        // ❗还有剩余数据没发完，继续监听EPOLLOUT，下次继续发
        ev.events = EPOLLOUT;
        epoll_ctl(MOD, &ev);
    }
    return count;
}
```

# 内核缓冲区满了是什么意思？

把TCP连接想象成**两根水管**：

> 服务器 ↔ 客户端 每一端都有两个**内核自带的蓄水池（缓冲区）**，**由操作系统内核管理，不在你的程序内存里**：

1. **内核接收缓冲区（recv buffer）**：别人发给你的数据，先放到这个池子，你的`recv()`函数从池子里捞数据。
2. **内核发送缓冲区（send buffer）**：你调用`send()`，不是直接把数据发给对端，而是**把数据拷贝进这个池子**，操作系统内核会在后台，自动把池子里的数据通过网卡慢慢发给客户端。

你截图里说的**内核发送缓冲区满了**：这个蓄水池已经装满了，放不下新的数据了。

## send函数到底干了什么（重点！很多人误解）

> ❌ 错误理解：`send()`调用 → 直接把数据通过网线发给客户端。 ✅ 真实行为：`send()`只是**把你的应用层buffer里的数据拷贝一份，放进操作系统内核的发送缓冲区**。拷贝成功，send函数就返回了。**至于客户端有没有收到，send函数根本不管，那是内核TCP协议栈后续的工作。**

### 两种场景解释

1. **内核发送缓冲区还有空位** 你的数据成功拷贝进去，send立刻返回，程序继续往下跑。内核后台慢慢把池子的数据发走。
2. **内核发送缓冲区满了（池子装满）** 为什么会满？ 客户端**接收速度跟不上服务器发送速度**。 客户端的内核接收缓冲区满了 → TCP的滑动窗口通知服务器：不要再发新数据了。 服务器这边内核发送缓冲区的数据没法投递出去，越堆越多，直到**池子填满**。

这时就分阻塞/非阻塞socket：

- **阻塞socket（你现在代码默认就是阻塞）** `send()` 函数**卡住不返回**，一直等待池子腾出空间。
    
    > 灾难：你的epoll是单线程事件循环！一旦send卡住，`epoll_wait`、其他所有连接的事件全部停止处理 → 整个服务器卡死。其他客户端全都连不上、没响应。
    
- **非阻塞socket** 池子满了，`send()`**不会阻塞，直接立刻返回-1，并且设置errno=EAGAIN**。 含义：**当前缓冲区暂时没空，这次发不了，你稍后再试**。
    
    > 问题：如果你没有在用户程序里保存这份待发数据，那这份数据就丢了！ ✅ 解决方案：**用户层缓冲区（就是你代码里connlist[fd].buffer）**，把没发完的数据保存在应用层，注册EPOLLOUT事件。等内核发送缓冲区有空位的时候，epoll触发EPOLLOUT，再次调用send_cb继续发送剩下的数据。
    

---

## 内核缓冲区 vs 你代码里的connlist[fd].buffer（用户缓冲区）

1. **内核发送缓冲区**：操作系统内核维护，在内核内存。`send/recv`系统调用会读写它。**大小有限，由系统参数控制**。
2. **connlist[fd].buffer**：**应用层（用户态）内存**，是你C代码里定义的数组。内核不能直接访问。
    
    > 当内核缓冲区满了的时候，我们就把待发送数据先放在**用户层buffer**，不要丢，等EPOLLOUT事件来继续发。这就是Reactor分离recv_cb/send_cb的根本目的。
    

## 举个生活例子

你（服务器程序）要给朋友（客户端）寄一堆书：

- **内核发送缓冲区 = 家门口快递柜**
- send = 把书放进快递柜。
    - 柜子有空：放进去，send返回，快递员（内核TCP）后续自己送货。
    - 柜子满了：
        - 阻塞模式：你就站在快递柜门口死等，等有人取走柜子里的包裹腾出位置，你才能放书。**你不能干别的任何事情**。对应epoll主线程卡死。
        - 非阻塞模式：快递柜满了，直接告诉你放不下。你不能原地等，要把书拿回自己家里（你的connlist用户buffer），等快递柜有空位通知你（EPOLLOUT事件），你再来放剩下的书。

## 补充一个容易混淆的知识点

EPOLLOUT事件的触发条件：**socket内核发送缓冲区有空闲空间**。 LT水平触发：只要有空位，epoll_wait就会一直上报EPOLLOUT事件。这就是你之前代码无限发送的根源。

## 一句话总结

内核发送缓冲区就是操作系统帮TCP连接维护的一块内存，用来做发送缓冲。当对端接收太慢，这块内存堆满后，阻塞socket的send会卡住整个epoll事件循环；非阻塞socket的send会直接失败返回EAGAIN。所以我们需要**用户层缓冲区 + EPOLLOUT事件**来保存待发数据，等缓冲区有空再继续发送。
